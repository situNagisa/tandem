# Tandem 产品定义

> 状态：草稿，待产品所有者确认。这里描述"我们在做什么、要做到什么程度"，不描述界面怎么画。规格与代码不一致时以这里为准。

## 产品是什么
Tandem 是一个**工作站服务**：跑在一台服务器上；用户用客户端（桌面、浏览器、手机）连接它；它连接各台**主机**，agent 在主机上执行。会话、账号、模型调用都在工作站；主机只负责执行命令与读写文件。

## 领域：按"拥有哪些概念"划分
每个概念只属于一个领域；其他领域只能引用，不能各自定义或各自计算。

| 领域 | 拥有的概念 | 依赖 |
|---|---|---|
| HOST 工作站与主机 | 工作站、账号、主机、执行器、设备 | — |
| MODEL 模型 | 模型账号、分组、模型能力（强度/上下文）、价格 | HOST |
| EXEC 执行 | 工具调用的执行、权限与审批规则、改动与 worktree | HOST |
| CONV 会话 | 会话、轮、消息、上下文、会话所在的主机与目录 | HOST、MODEL、EXEC |
| TREE 会话树 | 分叉、子代理、会话之间的关系 | CONV |
| AUTO 自动化 | 看板卡片、定时任务、评测 | CONV、TREE |
| NAV 查找 | 搜索索引、收件箱事件 | CONV、TREE |
| DEBUG 反馈（仅调试版） | 反馈条目、调整清单 | 全部（只读） |

依赖只能向上（表格从上到下），不能出现环。

## 界面不是领域
侧栏、会话区、输入框、右栏、设置页、顶栏是**界面**：它们把多个领域的功能摆在一起。界面不拥有概念；设置页里的每一项属于它所配置的那个领域。界面布局写在设计文档里，不写在这里。

## 写什么、怎么约束
每个功能用自然的文字写清楚，不套固定模板。内容分三种，写的时候说明是哪一种：
- **必须**：能判断对错的东西——概念归属、行为（"点 X 会到 Y"）、产品所有者定过的取法。用编号，用测试守住。
- **意图**：说不死、但有方向的东西——"像 git 图那样一眼看懂""安静不抢眼""像 Obsidian 那样编辑"。写清目的，附参考（参考产品、已认可的截图）；不用测试判断，由产品所有者看图认可。
- **自由**：没写到的都是自由的，实现者自己判断，只要不违背上面两种。产品所有者看了不满意，再把它变成意图或必须。

已认可的截图放在 `product/approved/<领域>/`，是意图的参照物；改动影响到这些画面时，要附前后对比请产品所有者确认。

## 维护规则
1. **加功能**：先找它拥有的概念属于哪个领域，放进那个领域。只有出现一个现有领域都不拥有的新概念，才允许新增领域，并在上表登记它的概念与依赖。
2. **一个概念只有一份实现**：会话树、轮、运行状态、模型能力、滚动位置这类被多处使用的东西，由所属领域提供，其他地方只读。
3. **反馈先归位**：没达到某条效果或行为 → bug；要改效果、行为或定过的取法 → 规格变更，先改这里、产品所有者确认后再实现。
4. **规格变更单独提交**，以 `spec:` 开头。
5. **测试名以行为编号开头**；检查脚本保证每条行为有测试、每条测试对应现存行为、领域表无重复概念且依赖无环。
6. **总量预算**：本文件 ≤80 行，每个领域 ≤150 行。写不下说明该重新划分，而不是继续加。
7. **派任务**：只引用编号与参照图（"满足 TREE-1/2；对照 approved/tree/…；其余自由"），协调者的理解不进任务；验收测试先由协调者写好，实现者不改；合并前由另一个子代理对照规格逐条审。
8. **漏检**：每次"检查全过但产品所有者发现问题"记入 `escapes.md`。
