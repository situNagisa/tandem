# 性能专项 v1（2026-11-07）

> 方法：临时 Host（`TANDEM_HOME=/tmp/tandem-perf`、端口 8261）+ 本地 OpenAI 兼容 SSE mock；
> Playwright（Chromium headless 1440×900）取页面内 `performance` / longtask / rAF 数据；
> Host 侧 Node 计时 + `perf_hooks.monitorEventLoopDelay`。所有夹具在 `/tmp` 生成，不碰真实数据。
>
> 复现：`node docs/archive/perf/scripts/perf-setup.mjs all` → `node docs/archive/perf/scripts/perf-v1.mjs before|after` →
> 聚焦项 `node docs/archive/perf/scripts/perf-ui-focus.mjs`。结果 JSON 在 `/tmp/perf-<tag>.json`。

## 2. 长会话（1000 轮 / 每条工具输出 30KB）

| 指标 | 优化前 | 优化后 | 说明 |
|---|---:|---:|---|
| 每次落盘（saveNow，含 fsync） | **129–169ms** | **0.4–0.7ms** | 首次从旧格式迁移需 133ms，一次性 |
| 异步写盘 | 140ms | 1.2ms | 同上 |
| 会话文件 | 31.9MB 单 JSON，每次整份重写 | 1.2KB 元数据 + 33.5MB 追加日志 | 每步只追加 30KB 左右 |
| 启动加载全部会话 | 95–105ms | 130ms | 回放 JSONL +25ms（换取写盘 200 倍提升） |
| `GET /api/sessions/:id`（31MB 全量） | 356–833ms | 319ms | 协议未改，仍一次性下发 |
| 前端打开会话 | 1811ms | **877–1015ms** | 首屏只渲染最近 60 条，历史分批补 |
| 打开时最大长任务 | **1129ms** | **160–193ms** | |
| 滚动帧时间 p50 / p95 | 30.1 / 33.4ms | **16.6 / 18.6ms** | 常驻消息上限 400 条（原 3000 行 / 10.5 万节点 → 301 行 / 1.35 万节点） |
| 流式输出总时长（同一 mock） | 5821ms | **1368ms** | 客户端按 30ms 合并 delta |
| 流式期间最大长任务 | **908ms** | **98ms** | |
| 流式期间主线程忙（longtask 合计） | 2177ms | **365ms** | |

做了什么：
1. **会话存储改为追加写**（`packages/server/src/store.ts`）：`sessions/<id>.json` 只存元数据，
   消息写入 `<id>.jsonl`，每行一批消息；按消息 id 幂等回放（同 id 后者覆盖），
   支持原地更新最后一条；长度回退（rewind）或追加日志超过快照 1.5 倍且 >8MB 时压实重写。
   旧格式首次保存自动迁移，读路径兼容旧 JSON。
2. **长会话渐进渲染**（`MessageList.tsx`）：≤400 条的会话一次渲完（保持打开即贴底）；
   更长的首屏 60 条，每 30ms 补 150 条，常驻上限 400 条，更早历史通过
   「加载更早的 N 条消息」按钮按需加载。行组件 `memo`，滚动时屏幕外行跳过排版。
3. **流式增量合并**（`serverMessages.ts`）：`block_delta` 30ms 批量应用；单条消息更新从
   `messages.map` 改为 `findIndex + slice`；避免每个 SSE chunk 重渲染上千行。

## 3. 多会话（200 Tandem + 3000 外部）

| 指标 | 优化前 | 优化后 | 说明 |
|---|---:|---:|---|
| 侧栏首行出现 | 157–163ms | 157–174ms | 未变 |
| 外部会话入口出现 | 335–461ms | 329–459ms | 冷启动解析 3000 文件仍占大头 |
| 侧栏最大长任务 | 55ms | 53–55ms | 外部会话默认每项目只露 5 条 |
| Ctrl+K 打开 | 33ms | **18–26ms** | |
| Ctrl+K 输入过滤 | 20ms | **10–21ms** | 结果只渲染前 60 条，无需虚拟列表 |
| 搜索最大长任务 | 0ms | 0ms | |

结论：在 200 + 3000 的规模下侧栏与搜索本身不是瓶颈（搜索只渲染 60 条、外部会话默认折叠 5 条），
**没有**为它们引入虚拟列表，避免无收益的复杂度；大目录文件浏览器用 CSS `content-visibility` 处理。

## 4. 并发（10 个会话同时流式）

| 指标 | 优化前 | 优化后 | 说明 |
|---|---:|---:|---|
| 10 轮总耗时 | 1031ms | 981ms | mock 端节流决定 |
| WS ping p99 | 15.6ms | **10.2ms** | |
| WS ping max | 58.1ms | **12.4ms** | |
| 事件循环延迟（整轮测量序列，p99） | 124ms | 129ms | 峰值来自前序 31MB 会话序列化后的 GC，不是并发路径 |
| 事件循环延迟（单独 10 会话，p99） | — | **22ms**（p50 10.1ms） | `monitorEventLoopDelay` 250ms 窗口 |

并发路径本身健康；整轮序列的高 p99 是前面大响应/大仓库扫描留下的 GC 峰值。持久化改追加写后、
扫描后 RSS 从 470MB 降到 241MB，GC 压力相应下降。

## 5. 未做 / 已知取舍

- `GET /api/sessions/:id` 仍一次返回全部消息（31MB）。进一步可做消息分页，但涉及协议与断线重放语义，
  本轮先用渐进渲染解决，首屏已可用。
- 长会话常驻 DOM 上限 400 条：更早消息需点「加载更早」。这是为了 60fps 滚动做的显式取舍，
  不影响数据与导出。
- 会话启动加载比旧格式慢约 25ms（回放 JSONL）；换来每次落盘从 130ms 降到 <1ms。
- 未做服务端事件广播合并（客户端已 30ms 合并）；10 会话隔离压测未发现事件循环瓶颈。
