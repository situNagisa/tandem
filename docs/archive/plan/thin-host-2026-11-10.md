# 瘦执行器：远端机器只跑单文件执行器（设计与原型）

> 更新：2026-11-10。一次性设计记录，写完即冻结。状态：草案，待产品经理拍板（第 8.3 节）。
> 本次只产出本文与原型 `/tmp/thin-exec`，未改产品代码、未提交。
> 产品依据（用户原话）：远端机器"不需要在主机上执行 node 任何相关的程序，只需要让主机运行完这条指令后，工作站能通过 ssh 等方式登录主机即可操作主机了"；"工作站去处理这些事务，端到端也要加密，但是加密的是工作站到主机间的通信"。

## 0. 摘要

- 新形态：agent 循环、会话存储、工具逻辑、模型调用全部在工作站。远端每台机器只放一个 `tandem-exec`：单文件、无运行时依赖、用户目录安装、不需要管理员，主动出站连工作站；链路加密并双向认证。
- 原型：Node 22 SEA 产出 linux-x64（119.2 MiB）与 win32-x64（83.2 MiB）单文件；bun --compile 产出 linux-x64（104.1 MiB）。两个 Linux 产物与 Windows 产物（经 WSL 互操作运行）各通过 14 项回环用例，覆盖 exec、退出码、UTF-8、1 MiB 二进制读写、并发、流式输出、kill、断线重连。
- 主要代价是体积：gzip 后 Node SEA linux 39.7 MiB、win 31.6 MiB。
- 原型纠正了一个设计点：Windows 上把命令作为参数交给 cmd 时，中文输出是 GBK；改写成 UTF-8 `.cmd` 文件后输出是 UTF-8（第 1.6 节）。

## 1. 执行器协议

### 1.1 形态

- 单文件，Node 22 SEA 注入；打包进 `ws`（纯 JS 回退，原生可选模块不装）。
- 只出站，不监听任何端口。当前主机是回环随机端口 + 工作站隧道，执行器不需要这一层。
- 用户态运行，不需要管理员，不需要防火墙规则（没有入站就不需要放行）。

### 1.2 链路与认证

每次连接做一次握手：

1. 执行器发 `HELLO{v, eph}`，`eph` 为 X25519 临时公钥。
2. 工作站回 `WELCOME{eph, sig}`，`sig = Ed25519(工作站私钥, transcript)`，`transcript = "tandem-exec-v1|hostId|eph_exec|eph_ws"`。执行器用安装令牌里的工作站公钥指纹核对公钥，再验签：**执行器校验工作站**。
3. 执行器发 `AUTH{execId, sig}`，`sig = Ed25519(执行器私钥, transcript)`。工作站用登记的执行器公钥验签：**工作站校验执行器**。
4. X25519 得共享密钥，HKDF-SHA256 派生两个方向的 AES-256-GCM 密钥。此后每帧加密，nonce = 方向前缀 + 64 位计数器，计数器溢出即断开。

- 算法与 E2E v1 相同（`packages/protocol/src/wire.ts` 的 X25519 / Ed25519 / HKDF / AES-256-GCM），不引入新原语。
- 首次加入：安装令牌形如 `ach_<secret>.<fp>`，`fp` 为工作站公钥 SHA-256 前 16 位十六进制。执行器生成 Ed25519 身份，在握手之后用令牌兑换（一次性、15 分钟有效）。工作站登记 `hostId ↔ 执行器公钥`；之后每次连接只做签名挑战。令牌只在加密通道内发送。
- 传输层用 WSS：TLS 用于隐藏流量元数据。身份靠上面的应用层签名，执行器不依赖 TLS 证书链，内网自签证书即可。
- 边界变化：工作站可以看到会话内容（用户已决定）。`docs/workstation.md` §1、§4、§8 的"工作站看不到会话内容"描述需要在批准后改写，本次未改。

### 1.3 帧与流控

- 帧：`[type u8][streamId u32][payload]`，沿用 `workstation/tunnel` 的线格式。控制信息为 JSON，数据为原始字节，不经 base64（原型已验证，省 33%）。
- 每个请求一个 streamId；单连接最多 32 个并发流，超出排队。
- 每流 1 MiB 接收窗口（同 `RES_WINDOW`）；接收方每消费 256 KiB 回 `FLOW`。单连接发送缓冲超过 4 MiB 时暂停读取子进程输出（原型已验证：1 MB 输出流式回传正常）。
- 块大小 64 KiB。大文件用 `fs.read` 的 offset/length 分块，不整体载入内存。

### 1.4 操作（v1）

| 操作 | 输入 | 输出 | 说明 |
|---|---|---|---|
| `exec.shell` | command、cwd、env、timeout、wrap（沙箱包装 argv） | OUT* + EXIT | Bash 工具。Windows 写 UTF-8 `.cmd` 后执行（第 1.6 节） |
| `exec.argv` | file、args[]、cwd、env | OUT* + EXIT | git / rg / gh / adb，不经过 shell |
| `cancel` | 流 id、signal | — | 杀进程树：POSIX 进程组；Windows `taskkill /T /F` |
| `bg.start / bg.log / bg.kill / bg.list` | — | RESULT | 后台任务由执行器持有：输出落 `~/.tandem-executor/tasks/<id>/`；断线后继续运行；执行器重启时用 PID + 进程启动时间核对，避免 PID 复用 |
| `fs.stat / fs.list` | path | RESULT | 文件树、Read 前检查 |
| `fs.read` | path、offset、length | RESULT（分块） | |
| `fs.write` | path、bytes、mode、expectMtime | RESULT | 临时文件 + rename；`expectMtime` 用于发现并发修改 |
| `fs.mkdir / fs.rename / fs.remove` | — | RESULT | |
| `fs.walk` | root、ignore[]、maxEntries | STREAM | Glob/Grep 在执行器侧遍历，避免逐目录往返 |
| `sys.info` | — | RESULT | os、arch、home、tmp、shell，git/rg/bwrap 是否可用，版本 |
| `fwd.open` | host、port | 双向字节流 | 仅 v2，用于浏览器预览的端口转发 |
| `pty.*` | — | — | 仅 v2，按需 |
| `update.fetch` | version | 分块 | 自更新 |

### 1.5 心跳、重连、版本、自更新

- 心跳：工作站每 15 秒 PING，45 秒无 PONG 则断开。原型用 5/15 秒只是为了测试快。
- 重连：断开后退避 1 → 2 → 4 … 最长 30 秒，加 ±20% 抖动，重连后重新握手。
- 断线语义：未结束的 exec 流杀掉进程树（原型行为）；后台任务不受影响；工作站侧该工具调用返回"连接中断"，agent 循环继续。
- 版本协商：HELLO 带 `v:[min,max]` 与能力列表，WELCOME 返回选定版本与能力交集。不在能力列表里的操作返回 `EUNSUPPORTED`（非致命）。v1 内只增不改；破坏性变更才升 v2。
- 自更新：只在没有运行中的流、没有后台任务时进行。工作站提供 manifest（版本、平台、sha256），经已认证通道下载并校验。Linux 用 rename 替换；Windows 不能覆盖运行中的 exe，先把旧文件改名为 `.old`，写入新文件，拉起新进程后退出旧进程。

### 1.6 原型结论与差距

- **Windows 命令编码**：把命令当参数交给 `cmd /d /s /c "chcp 65001 >NUL & <命令>"`（与 `util/encoding.ts` 的 `cmdUtf8Command` 同形）时，含中文的输出是 GBK（实测字节 `c4e3bac3`）。把同一命令写进 UTF-8（无 BOM）的 `.cmd` 文件，首行 `@echo off`、次行 `chcp 65001>nul`，输出是 UTF-8（`e4bda0e5a5bd`）。现有 Host 的 Windows Bash 工具用的就是 `cmdUtf8Command` 这种写法，输出靠 `decodeProcessOutput` 的 GBK 回退兜底（`util/encoding.ts` 注释即此原因）。执行器采用 `.cmd` 方式；工作站保留回退解码。
- **未验证**：批处理文件对单独 `%` 的解释与命令行不同，需要转义规则（M3 测试项）；用户名含空格的临时目录路径；超长路径。
- **原型未覆盖**：加密握手与身份登记（原型为明文回环，只验证了 HELLO、帧、流和操作）；macOS 与 arm64 未构建；Windows 测试经 WSL 互操作运行，不是原生 Windows 会话；Defender 与 SmartScreen 行为未验证。

## 2. 工作站侧

### 2.1 远端 Host 上下文

每台远端机器对应一个 `RemoteHostContext`（工作站内，按 hostId 缓存），实现统一接口 `HostEnv`：

```ts
interface HostEnv {
  platform: 'linux' | 'darwin' | 'win32';
  path: typeof path.posix | typeof path.win32; // 远端路径语义
  home: string;
  tmp: string;
  exec(req: ExecRequest): ExecStream;          // shell 或 argv
  fs: { stat; list; read; write; mkdir; rename; remove; walk };
  bg: { start; log; kill; list };
}
```

- `LocalHostEnv` 用 `node:fs` / `child_process` 实现同一接口。个人模式（工作站与主机同机）与现有本地模式行为不变。
- 工具只调用 `ctx.env`，不再直接 import `node:fs` 或 `child_process`。远端与本地走同一份工具代码。
- 每个会话绑定一个 env（`session.hostId`）。工作站上的会话、消息、检查点、记忆按 `hostId + 项目绝对路径` 归属，不写远端的 `~/.tandem`。

### 2.2 注入点与路径语义

- 注入：`packages/server/src/types.ts:261` 的 `ToolContext` 增加 `env: HostEnv`；`tools/index.ts:136` 的 `executeTool` 原样传入，签名不变。调用点 `agent/loop.ts:1199` 与 `agent/resume.ts:317` 只需从会话取出 env 再传。
- 路径：`util/path.ts` 有三处全局假设，需要改成从 env 取值：
  - `:5 expandHome` 用 `os.homedir()`，应改为 `env.home`；
  - `:11 resolvePath` 用 `path.resolve`，即运行方系统的语义。远端 Windows 路径在 Linux 工作站上会被错误解析；
  - `:25 hostPathOf` 与 `:29 HOST_PATH` 默认取 `process.platform`，应由 `env.platform` 决定。
  - `:37 normalizeIncomingPath` 已接受 `platform` 参数，可直接沿用。
- 影响面（实测）：`process.platform` 出现在 21 个文件中，`os.homedir()` 出现在 15 个文件中。每一处都要判断是"宿主机自身"（保留）还是"项目所在机器"（改走 env）。
- Web 文件树与 `routes/fs.ts`（5 处路径辅助调用）也要走 env，否则远端项目的文件列表看不到。

## 3. 数据迁移与新旧并存

### 3.1 旧数据在哪

每台远端机器上的旧完整 Host 把数据放在 `~/.tandem`（开发版、桌面版）或 `~/.tandem-host/data`（安装版）下：

- `sessions/<id>.json` 与 `<id>.jsonl`（会话元数据与分段消息）、`checkpoints/`、`tasks/`（后台日志）、`memory/`、`wiki/<hash>/`、`boards/`、`evals/`、`index/search.json`、`skills-state.json`、`browser.json`、`secrets.json`（加密，解密密钥的位置需先确认）。
- 模型账号在上一版已迁到工作站，不再迁移。`accounts.json`（主机身份）不迁，由执行器重新登记。

### 3.2 导入流程

1. 执行器 `join` 完成后，工作站用 `fs.list` 列出上述目录，给出数量与总大小，由用户确认再开始。
2. 工作站用 `fs.read` 分块拉取，支持断点续传，写入工作站存储。会话 id（UUID）保持不变。
3. 会话记录增加 `hostId` 与 `projectRef`（hostId + 远端绝对路径 + 平台）。`cwd` 字符串保持原样，路径语义按原平台解释。
4. 导入幂等：以文件 sha256 为键，重跑时跳过已导入文件。工作站已有同 id 的记录时以工作站为准，与模型账号迁移的规则一致。
5. 旧目录只读，不删除。工作站账本记录导入时间与文件清单。
6. 对账：会话数、消息数、每个 jsonl 的行数与 sha256 在导入页显示。

### 3.3 新旧并存

- 同一台机器同一时间只允许一个执行入口（旧完整 Host 或执行器）接收新会话。两个 agent 同时修改同一仓库，工作站无法协调。
- 执行器接入时，若同一账号下该机器已有旧主机登记，工作站把旧主机标为"已迁移"：不再接受新会话，已有会话只读、可导出。旧进程由用户自己停止，执行器不结束别的进程。
- 导入未完成前不标记迁移，避免丢会话。
- 新执行器上线即为新路径。旧完整 Host 对远程机器保留到删除时点（第 3.4 节）。本地模式（工作站与主机同机）不受影响。

### 3.4 删除时点（建议，待拍板）

- 旧完整 Host 的远程连接路径：执行器达到 GA 后保留两个小版本，然后移除远程连接代码。
- 导入窗口：移除后旧目录仍只读保留 90 天，之后由用户自行删除。
- 本地模式（个人模式内嵌工作站 + 主机）不删除。

## 4. 安装

### 4.1 一行命令

与现有 `workstation/installScripts.ts` 的形式相同，替换的是安装内容：从整包 `tandem-host.tgz` 改为单文件 `tandem-exec`。

```bash
curl -fsSL http://<工作站>:8481/install.sh | sh -s -- --token ach_…
```

```powershell
& ([scriptblock]::Create((irm http://<工作站>:8481/install.ps1))) -Token 'ach_…'
```

开机自启参数不变（`--service` / `-Service`）。

### 4.2 步骤

1. 检测系统与架构，映射到目标名（`linux-x64`、`darwin-arm64`、`win32-x64` 等）。不支持的组合直接报错。
2. 下载 `<工作站>/executor/<target>.gz`（Linux 39.7 MiB，Windows 31.6 MiB）。sh 用 `gzip -d`；ps1 用 .NET `GZipStream`，PowerShell 5.1 可用。
3. 校验 sha256。哈希由工作站生成脚本时写进脚本，每个平台一条，不另取清单。校验工具依次回落 `sha256sum` → `shasum` → `openssl`，都没有就失败，不静默跳过。
4. 解压到 `~/.tandem-executor/bin/tandem-exec`（Windows：`%USERPROFILE%\.tandem-executor\bin\tandem-exec.exe`），权限 755。已有旧文件先改名挪开（Windows 运行中不能覆盖）。
5. 前台运行 `tandem-exec join --server <工作站> --token <令牌>`：握手，兑换令牌，写身份文件 `~/.tandem-executor/identity.json`（0600），连接，打印"已连接工作站 X，主机名 Y；关闭此窗口即断开"。
6. 可选 `--service`：Linux 写 `systemd --user` 单元（`Restart=always`）；用户 linger 需要管理员权限，没有时只提示；macOS 写 LaunchAgent；Windows 写当前用户的 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`（与 `docs/workstation.md` §3 一致）。
7. 重复执行幂等：身份文件不覆盖；已在线的执行器不再起第二个进程。

远程机器不再需要 Node.js ≥ 22（`docs/workstation.md` §3 当前要求）。

### 4.3 可照搬 AIPL 参考脚本的部分

参考文件：`/tmp/aipl-ref/install.sh`、`/tmp/aipl-ref/install.ps1`（只读）。

- POSIX `sh`，不用 bash 专有语法与 `pipefail`；每步显式判返回码。
- 交互只读 `/dev/tty`，因为 `curl | sh` 时 stdin 是脚本本身。
- 下载失败、404、哈希不符都直接报错，不回落到只比较文件大小。
- 重跑只升级二进制，不动凭据文件（AIPL 的 `auth.json` 规则）。
- Windows：先启用 TLS 1.2（5.1 默认不启用）；脚本以 ASCII 或带 BOM 的形式下发，防止中文被误解码（AIPL 有解码自检）。
- 替换运行中的 exe 前检查进程（Windows 上会锁文件）。

### 4.4 不照搬的部分

- 不要 TOFU 横幅与 minisign。AIPL 从公网下载才需要它们。这里下载源是工作站（内网），信任根是令牌里的工作站公钥指纹。
- 不要防火墙规则。执行器只出站、不监听端口，不需要放行（AIPL 的设备网关才需要）。
- Windows 自启用 HKCU Run，不用计划任务（AIPL 用计划任务，我们沿用 `docs/workstation.md` 已定的 HKCU 方案）。

## 5. 留在工作站、远端执行、本版不支持

以下是给产品经理采纳的默认建议。

| 能力 | 默认 | 理由 / 条件 |

| Agent 循环、会话、审批、模型调用、界面 | 工作站 | 核心改动 |

| Bash、文件读写、Glob/Grep、git、hooks、skills 与外部会话读取 | 远端执行 | 文件在远端 |

## 6. 里程碑与验收

每个里程碑可独立交付、独立回归。

- **M1 执行器 v1（不接产品）**
  - 验收：linux-x64 与 win32-x64 单文件；第 1.4 节的 exec、fs、cancel、sys 操作；加密握手；令牌兑换；断线重连。
  - 回归：原型 14 项在 Linux 与 Windows 各跑一遍。新增认证用例：错误工作站公钥被拒、伪造执行器签名被拒、重放握手被拒、篡改密文后断开。1 GiB 文件分块读写的内存有上限。32 并发流。
  - 构建：两平台 `.gz` 与 sha256 由构建脚本产出；`--version` 可用。
- **M2 远端上下文与只读工具**
  - 验收：`LocalHostEnv` 与 `RemoteHostContext` 通过同一组接口测试。Read、Glob、Grep 在远端 Linux 与 Windows 上的结果与同一仓库的本地结果一致。路径用例覆盖盘符、反斜杠、中文名、大小写、空格、符号链接。
  - 回归：`npm run test:server`、`node scripts/check.mjs --skip-smoke`；`e2e/regression.mjs` 的工作站用例不变。
- **M3 写与执行**
  - 验收：Write、Edit、Bash、BashOutput、KillBash 远端可用。审批流程（Bash、Write 审批卡）在远端会话中端到端跑通。检查点可回退远端文件。后台任务断线后继续运行，且能读到日志。Linux 与 Windows 上都能杀掉进程树。
  - Windows `.cmd` 用例：中文、`%`、管道、重定向、退出码、用户名含空格的临时目录、超长路径。
  - 沙箱：Linux 远端 bwrap 包装生效；未安装 bwrap 时给出提示。
- **M4 状态迁移与其余工具**
  - 验收：Memory、Todo、Task、WebFetch、Wiki、Skill 对远端项目可用。第 3.2 节导入对账一致（会话数、消息数、jsonl 行数、sha256）。旧主机标记迁移后不再接受新会话。`external.ts` 只读导入远端 `~/.claude`。
  - 回归：`e2e/regression.mjs` 的工作站与任务看板用例；导入重跑无变化。
- **M5 设备与浏览器（v2）**
  - 验收：远端 adb 的 devices、shell、install、logcat 可用；浏览器预览经 `fwd.open` 访问远端 localhost。串口若需要，单独立项。
- **M6 移除远程连接的旧完整 Host 路径**（时点见第 3.4 节）
  - 验收：删除前两个版本回归全绿；删除后远程机器只能经执行器接入；本地模式回归不变。

## 7. 风险

1. **工作站集中了会话内容**。工作站被攻破即意味着会话内容泄露，这在之前不是。缓解：工作站只部署在内网，主机侧审计，日志中不记录内容。这是产品层面的改变，需要确认。
2. **体积与下载**。Linux 单文件 119 MiB（gzip 39.7 MiB）。在本机的 npm 代理上实测约 0.5 MB/s，慢网络下首次安装要好几分钟。
3. **系统兼容**。Node 22 SEA 的 Linux 产物需要 glibc ≥ 2.28 与动态链接的 libstdc++，因此 Ubuntu 18.04（glibc 2.27）与 CentOS 7（glibc 2.17）上无法运行。bun 产物需要 glibc 2.17，但 Windows 版未测。
4. **签名与杀软**。官方 `node.exe` 带 Authenticode 签名；注入 blob 改动了文件内容，签名随之失效（postject 报 "signature seems corrupted"）。分发的 exe 需要重新签名，否则可能被 SmartScreen 或杀软拦截。macOS 需要重新签名，未测。
5. **Windows 编码与 cmd 语义**。`.cmd` 方案的 `%` 转义、路径空格、超长路径尚未全部覆盖（M3 测试）。cmd 启动本身有开销：本机经 WSL 实测，本地 cmd 平均 96 ms，执行器往返平均 207 ms。大量小命令的累计延迟会比本地明显。
6. **断线语义**。中断线时正在运行的 Bash 或写入如何收尾，当前原型是直接杀掉。需要在 M3 定稿。写入用临时文件加 rename 可以避免半写文件。
7. **双执行入口冲突**。同一项目被两个 agent 同时修改。第 3.3 节的互斥规则必须做成硬约束，不能只靠提示。
8. **工具测试矩阵**。31 个工具 × 3 个平台 × 本地/远端，测试量明显增加。要求每个迁移文件都带远端对照用例。
9. **自更新与孤儿进程**。Windows 替换运行中的 exe。执行器退出时要清理后台任务与子进程（Linux 进程组、Windows 进程树）。
10. **常驻权限**。执行器常驻并能以用户身份在远端执行命令，这与 Bash 工具的能力相同，但是常驻，工作站侧的审批与审计需要覆盖每一次远端调用。

## 8. 原型结果与待拍板

### 8.1 原型结果

原型位于 `/tmp/thin-exec`，Node 与 bun 运行时均来自 npm 平台包（`node-linux-x64`、`node-win-x64` @22.23.4；`@oven/bun-linux-x64` @1.4.4）。

| 产物 | 原始大小 | gzip -9 | `--version` 中位数 | 连接到 HELLO | 回环用例 | 备注 |
|---|---|---|---|---|---|---|
| `tandem-exec-linux-x64`（Node 22.23.4 SEA） | 119.2 MiB（strip 后 102.5 MiB） | 39.7 MiB | 25.8 ms（基线：node22 运行 cjs 27.5 ms） | 31–37 ms | 14/14 | 需 glibc ≥ 2.28 与 libstdc++ |
| `tandem-exec-win-x64.exe`（Node 22.23.4 SEA） | 83.2 MiB | 31.6 MiB | 143.9 ms（经 WSL 互操作） | 585–627 ms（不含拷贝 exe 的时间） | 14/14（经 WSL 互操作运行） | 只依赖系统 DLL，不需要 VC++ 运行库；原 node.exe 的官方签名注入后失效（见第 7 节第 4 条） |
| `bun-exec-linux-x64`（bun 1.4.4 --compile） | 104.1 MiB | 49.2 MiB | 15.3 ms | 16 ms | 14/14 | 需 glibc ≥ 2.17，无 libstdc++；Windows 未测 |

其他数据（均为 10 次或 200 次的顺序测量）：

- 往返延迟，200 次 `echo`：Linux SEA 平均 2.5 ms（p50 2.0，p95 3.9），本地 `bash -c` 平均 1.0 ms；bun 平均 1.44 ms。Windows 40 次：执行器平均 207 ms，本地 `cmd` 经 WSL 平均 96 ms，差距主要来自 cmd 启动本身。
- 1 MiB 随机二进制的写与读，sha256 校验一致：Linux 写 9–11 ms、读 9–14 ms；Windows 写 14–15 ms、读 12–13 ms。
- 并发：慢命令（sleep 2）运行中，快命令返回用时 Linux 54 ms，Windows 240 ms。
- kill：Linux 1.4–2.7 ms（进程组）；Windows 333–390 ms（`taskkill /T /F`）。
- 断线重连：服务端在同一端口重启后，执行器分别在 509 ms（Linux）与 545 ms（Windows）内回连并继续 exec。

14 项用例：HELLO 平台与版本、exec 基本输出、退出码与 stderr 分离与 UTF-8 中文、cwd 不存在、命令不存在、1 MiB 写与读、stat、list、读不存在的文件返回 ENOENT、并发、1 MB 流式输出、kill、断线重连。

复现：

```bash
cd /tmp/thin-exec
node build.mjs                                   # 需要 rt/linux、rt/win（npm pack 的 node-linux-x64、node-win-x64 @22.23.4）
node test/run.mjs linux dist/tandem-exec-linux-x64
node test/run.mjs win dist/tandem-exec-win-x64.exe
node test/bench-startup.mjs
```

注意：`npm pack` 解出的 `node.exe` 没有执行位，需要先 `chmod +x`。源码：`src/wire.ts`（43 行，线协议）、`src/executor.ts`（187 行，执行器）、`build.mjs`、`test/run.mjs`（回环服务端与 14 项用例）、`test/bench-startup.mjs`。

### 8.2 原型没有做的

加密握手与令牌登记、macOS 与 arm64、原生 Windows 会话、杀软与 SmartScreen、自更新、后台任务、PTY。这些都在第 1 节的协议里，尚未实现。

### 8.3 待拍板

1. **执行器运行时：Node 22 SEA，还是 bun --compile？**
   - 默认推荐 Node 22 SEA：与仓库同语言，工具代码可以直接复用，`child_process` 与 `fs` 行为与本地 Host 一致。代价是 Linux 需要 glibc ≥ 2.28。
   - 决定问题：目标机器里有没有 glibc 低于 2.28 的 Linux（如 Ubuntu 18.04、CentOS 7）？有 → 选 bun，并先补测 Windows 版；没有 → 选 Node 22 SEA。
2. **代码签名与最低系统版本。** 是否有公司代码签名证书用于 Windows exe（以及 macOS 开发者签名）？没有的话，Windows 用户首次运行会遇到 SmartScreen 警告，是否接受？
3. **v1 能力边界与旧 Host 删除时点。**
   - 远端 stdio MCP、远端浏览器预览、串口在 v1 不支持，是否同意？HTTP MCP 与 WebFetch 留在工作站。
   - 旧完整 Host 的远程连接路径：执行器 GA 后保留两个小版本，导入窗口只读 90 天，之后移除，是否同意？

若第 1 项未定，M1 的构建目标无法定稿；若第 2 项未定，Windows 版只能内测；若第 3 项未定，M2 之后的工具范围无法锁定。

## 9. 产品经理决定（2026-11-10）

1. **执行器语言改用 Go**，不用 Node SEA。理由：Node SEA 单文件 119 MiB、Linux 需 glibc ≥2.28（老系统跑不了）、注入后官方签名失效；Go 静态编译单文件约 5–10 MiB，无 glibc 依赖（CGO_ENABLED=0），一套源码交叉编译 win/linux/mac × amd64/arm64，与 AIPL 参考同一路线。工具链可经 go.dev / goproxy.cn 获取（已验证可访问）。执行器只做第 1.4 节的操作，不含业务逻辑，Go 代码量可控。
2. **Windows 暂不签名**，接受首次运行的 SmartScreen 提示；一行命令用 PowerShell 下载，不经浏览器，通常不触发 MOTW。是否购买证书仍在 HANDOFF「等用户决定」。
3. **v1 范围按第 5 节默认建议**：串口、远端浏览器预览、远端 stdio MCP 本版不支持；旧完整 Host 远程路径在执行器可用后保留 2 个小版本，导入窗口只读 90 天后删除（M6）。
4. 风险 1（工作站集中会话内容）已由产品所有者确认接受：加密的是工作站↔主机链路。
